# 실제 공영주차장 화면 연결

서울시 GetParkInfo와 교통안전공단 Parking_v1 시설/운영정보를 서버에서 수집해
`data/parking-combined-v1.sqlite`에 저장한다. 기존 출처별 DB와 혼용하지 않는다.

## 로컬 실행

.env에 SEOUL_PARKING_KEY와 TS_PARKING_SERVICE_KEY가 모두 필요하다.
사용자가 `npm run dev`로 서버를 실행한다. Node 22.13 이상이 필요하다.
Vite의 parkingPlugin이 GET /api/parking?lat=...&lng=...&radiusM=1000을 제공한다.
키는 서버에서만 읽으며 브라우저에는 주변 주차장 목록만 반환한다.
정적 배포/`vite preview`용 서버는 아직 제공하지 않는다.

## 갱신 방식 (개발 단계)

수집은 클릭마다가 아니라 **하루(KST) 한 번**이다. 같은 날에는 DB를 재사용하고, 같은 서버 내
동시 검색은 수집 한 번으로 합친다. 공단 응답량이 많아 전체 수집은 **수 분(실측 약 4분 46초)**
걸린다. 자동 실행 스케줄러는 없고, 상황별 동작은 아래와 같다.

| 상황                       | 동작                                                                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| DB가 비어 있음 (최초 실행) | 보여줄 데이터가 없으므로 수집이 끝날 때까지 기다린다. 한 출처라도 실패하면 HTTP 503                                                            |
| 같은 날                    | DB를 그대로 쓴다 (수집 없음)                                                                                                                   |
| **날짜가 바뀐 뒤 첫 검색** | **어제 데이터로 바로 응답**하고 뒤에서 갱신을 시작한다. 사용자는 기다리지 않는다                                                               |
| 뒤 갱신이 실패             | 오류 없이 기존 데이터를 계속 쓴다. 서버 로그에 `[parking] 뒤 갱신 실패 ...`를 남기고, 10분(`PARKING_REFRESH_RETRY_MIN`) 쉬었다가 다시 시도한다 |

> 이전에는 "오래된 DB나 샘플로 조용히 대체하지 않는다"였다. 개발 중에는 하루 첫 사용자가
> 몇 분 멈춘 화면을 보는 불편이 더 커서 위처럼 바꿨다. **샘플 데이터로 대체하는 일은 여전히 없다.**

주의:

- 날짜가 바뀐 직후에는 **하루 지난 시설·요금 데이터**가 보일 수 있다. 시설 정보는 하루 사이에 거의
  바뀌지 않고, 실시간 포화율은 별도 API(`/api/parking/live`)라서 이 영향을 받지 않는다.
- 뒤 갱신이 계속 실패하면 오래된 데이터가 계속 쓰인다. 서버 로그에서 `[parking]` 경고를 확인한다.
- 오래된 데이터라는 사실은 화면에 표시하지 않는다 (서버 로그에만 남는다).
- 브라우저는 최대 5분 기다린다. 빈 DB의 최초 수집은 이 한도에 근접할 수 있다.
- **배포 단계에서는 요청과 무관한 하루 1회 배치(예약 실행)로 옮겨야 한다.** 지금 방식은 개발용이다.

## 중복 처리

서울시 이름의 (시)/(구), 공영, 주차장, 공백을 제거한 이름이 공단과 같고 75m 이내이며,
양쪽에서 하나씩 대응되는 경우만 하나로 병합한다. 너무 일반적인 두 글자 미만 이름과
모호한 다대다 대응은 합치지 않는다. 전체 중복 제거를 보장하지 않는 보수적 매칭이다.
서울시 위치/이름/ID 및 유효한 요금을 우선한다. 서울시 요금이 없으면 일치한 공단
요금으로 보완한다. 각 출처의 관리번호가 서로 같은 체계라고 가정하지 않는다.

## 화면 연결과 한계

- createLiveJourneyService는 HttpParkingProvider를 사용한다. 테스트용 서비스는 샘플 유지.
- 도착지 2개 이상일 때 마지막 도착지 전까지 실제 주차장 선택을 진행한다.
- 기존 후보 선정으로 반경 1km에서 최대 3곳을 고르고 요금을 경로 계산에 전달한다.
- 단일 도착지는 기존 동작대로 주차 선택을 생략한다.
- park-transit는 기존 가정 기반 전략을 유지한다. 실제 선택 주차장/요금이 반영되지
  않는다는 별도 문구를 표시한다. 자차(차량 유지형)와 구분한다.
- 요금 미상은 null이며 무료가 아니다. 운영시간·할인·요일별 요금·잔여석은 미반영.
- 변경 후 서버를 재시작해야 새 서버 설정이 적용된다.

## 검증

외부 API 자동 테스트는 mock 처리한다. 병합, HTTP 입력 검증/실패 처리, 브라우저
provider, 실제 서비스의 주차장 provider 연결을 테스트한다.
기존 routing/summary.ts의 park-transit 라벨 누락으로 전체 앱 타입 검사가 실패하는
문제는 이번 주차장 연결 범위 밖이라 수정하지 않았다.

## 공단 페이지 응답 검증 (2026-11-04)

- 시설정보 totalCount는 238,045이나 마지막 페이지까지의 실제 항목 합은
  238,029였다. 1,000건/9,999건 페이지 크기 양쪽에서 같은 차이를 확인했다.
- 마지막 페이지의 양수 건수 차이만 허용하고, 그 다음 빈 페이지까지 추가 검증한다.
  중간 페이지 누락, 페이지 번호 불일치, 수집 중 totalCount 변경은 계속 실패 처리한다.
- 기본 페이지 크기는 9,999이며 요청당 60초, 통신/5xx 오류에 최대 3회 시도한다.
  인증/다른 4xx 오류는 재시도하지 않는다. 키와 원문 URL은 오류에 포함하지 않는다.

2026-11-04 실 API 적재 확인: 서울시 원본 2,167행 → 유효 고유시설 106곳,
공단 시설정보 238,029행 → 유효 공영시설 804곳. 출처 간 3곳을 병합해
총 907곳을 DB에 저장했다. 명칭에 나눔카·거주자 우선/전용이 명시된 시설은
일반 승용차 후보에서 제외한다. 이름 필터만으로 모든 이용 제한을 판별하지는 못한다.

화면 검증: 서울역 → 덕수궁길·정동길 → 강남역에서 실제 주차장 후보 3곳,
지도 마커, 거리·요금 미상 표기 및 선택 버튼을 확인했다. 시청 좌표 기준
/api/parking 응답 HTTP 200, 약 36ms(당일 DB 재사용)도 확인했다.
이후 사용자가 ODsay 등록 IP를 수정해 ApiKeyAuthFailed가 해결됐다.
2026-11-04 재검증에서 실제 대중교통 경로 23개 응답과 최종 비교 화면을 확인했다.
자차+도보 결과에 선택한 영국대사관옆 공영주차장 및 요금 정보 없음이 반영됐고,
대중교통 결과는 이동 49분·3,050원, 1호선/470번 버스 상세를 표시했다.
이 값은 해당 조회 시점의 결과이며 고정값이 아니다. park-transit의 실제 주차장
미반영 및 도보 추정 등 기존 범위 제한은 그대로다.
자동 테스트 226개 통과. 전체 앱 타입검사는 기존 routing/summary.ts 오류가 남아 있다.
